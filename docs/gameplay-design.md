# 语音角色对战游戏玩法设计

## 1. 文档信息

- 文档状态：首版单局模式规则草案
- 参考方向：实时语音念招式、角色技能对战
- 规则基线：不设计施法打断；允许技能在结算后附加一回合行动限制和其他状态效果
- 适用对象：产品、策划、客户端、战斗服务器、测试

本文档中的数值是首版建议值，正式上线前需要通过对局数据进行平衡调整。

## 2. 核心体验

玩家选择一个角色。每个角色拥有 1 个基础技能和 6 个角色技能，共 7
个技能。每回合双方同时开始念技能名称，服务器收到第一个“正确且当前可释放”的技能文本后，该玩家获得本回合行动权，另一方本回合不能行动。技能结算完成后进入下一回合。

游戏的核心决策是：

1. 选择适合当前局势的技能。
2. 在技能使用次数和重复间隔限制下安排出招顺序。
3. 通过更快、更准确地念完技能名抢到本回合行动权。
4. 通过伤害、治疗、护盾、增益、减益和特殊效果组合建立技能循环。

## 3. 玩法流程

本章是首版战斗流程的基准。数值、角色定位和技能效果可以调整，但必须遵守本章的阶段顺序和服务器权威边界。

### 3.1 单回合阶段总览

每个回合固定经过三个阶段：

| 阶段         | 服务器状态        | 主要工作                                                             | 结束条件                         |
| ------------ | ----------------- | -------------------------------------------------------------------- | -------------------------------- |
| 回合开始阶段 | `WAITING_COMMAND` | 等待客户端提交系统语音识别后的技能名称，并校验行动是否有效           | 收到第一个有效行动，进入战斗阶段 |
| 战斗阶段     | `SETTLING`        | 执行已接受的技能，根据行动和双方状态计算伤害、治疗、护盾及其他效果   | 本次行动效果计算并持久化完成     |
| 回合结束阶段 | `ENDING`          | 处理回合结束触发效果、状态持续时间和死亡检查，通知结果并决定下一回合 | 下一回合创建，或对局结束         |

单回合没有玩法时长限制。无效请求不会推进阶段；服务器会一直停留在
`WAITING_COMMAND`，直到收到有效行动或对局因终局、断线回收等原因结束。

### 3.2 单回合流程总览

```text
回合开始：WAITING_COMMAND
  -> 校验客户端技能名称和角色状态
  -> 无效：返回错误，继续 WAITING_COMMAND
  -> 有效：原子写入回合行动者

战斗阶段：SETTLING
  -> 执行行动
  -> 计算并应用行动结果
  -> 向双方通知行动者、行动内容和战斗结果

回合结束：ENDING
  -> 处理 DOT、周期治疗、Buff 持续时间等回合结束效果
  -> 检查死亡和对局结束
  -> 无死亡：创建下一回合
  -> 有死亡：结束对局
```

### 3.3 回合开始阶段

#### 进入阶段

1. 服务器确认对局状态为 `RUNNING`，双方角色仍存活。
2. 服务器创建当前回合记录，首回合为
   `round_no = 1`，后续回合在上一回合基础上递增。
3. 服务器将 `round_status` 设置为 `WAITING_COMMAND`，清空 `round_winner_id`。
4. 服务器向双方发送
   `ROUND_STARTED`，包含回合号、双方当前战斗快照和当前角色可展示技能。
5. 服务器检查双方是否带有“本回合不可行动”的状态；被石化、麻痹或冻结的一方标记为本回合跳过行动，但不影响另一方出招。若双方都被限制行动，则直接进入回合结束阶段。
6. 客户端等待可行动玩家喊出技能名称；客户端系统完成语音转文字后提交回合指令。

客户端提交的数据只包括身份、回合、`command_id`
和转写文字。客户端不能提交伤害、治疗、护盾、技能次数、命中结果或胜负结果。

#### 行动有效性校验

服务器收到请求后立即处理，不做防抖、不等待对手请求，也不等待固定的同时结算窗口。校验顺序如下：

1. 检查 `command_id` 是否已处理；已处理则返回原处理结果，防止网络重试重复结算。
2. 检查 `battle_id`、`round_no` 和玩家身份是否属于当前对局和当前回合。
3. 检查当前回合是否仍为 `WAITING_COMMAND`；对方已经成功行动时返回
   `ROUND_ALREADY_WON`。
4. 检查行动者角色是否存活；死亡角色不能行动。
5. 检查行动者是否带有本回合行动限制；若处于石化、麻痹或冻结状态，返回
   `ACTION_DISABLED`，不占用行动权。
6. 将转写文字与行动者角色的标准技能名称精确匹配；匹配失败返回 `ASR_FAILED`。
7. 检查技能是否满足使用规则：普通技能是否已用过、基础技能是否在上一回合使用过、特殊技能是否达到次数或间隔限制。
8. 通过数据库行锁、乐观锁版本号或房间单线程事件循环，原子写入 `round_winner_id`
   并将状态改为 `SETTLING`。

只有第 7
步成功的请求才算本回合有效行动。无效请求不会消耗技能次数、不会产生效果，也不会阻止之后的有效请求。

#### 校验结果

| 校验情况                       | 返回结果                     | 回合处理                       |
| ------------------------------ | ---------------------------- | ------------------------------ |
| 技能文字不是标准技能名称       | `ASR_FAILED`                 | 继续等待                       |
| 普通技能已经使用过             | `SKILL_EXHAUSTED`            | 继续等待                       |
| 基础技能上一回合使用过         | `BASIC_CONSECUTIVE_REJECTED` | 继续等待                       |
| 特殊技能次数或间隔不满足       | `REUSE_LIMIT_REJECTED`       | 继续等待                       |
| 对手已先获得行动权             | `ROUND_ALREADY_WON`          | 不再处理本回合行动             |
| 行动者已经死亡                 | `ACTOR_DEAD`                 | 不产生行动                     |
| 行动者本回合被石化、麻痹或冻结 | `ACTION_DISABLED`            | 该玩家跳过行动，另一方仍可行动 |
| 校验通过并原子抢到行动权       | `ACCEPTED`                   | 进入 `SETTLING`                |

#### 并发处理

两个请求几乎同时到达时，以服务器战斗房间实际处理有效请求的顺序为准。`round_winner_id`
只能成功写入一次；客户端的语音开始时间、念完时间和请求发送时间不能覆盖服务器的原子判定。

每场对局必须以 `battle_id` 作为唯一主键保存一份服务端权威快照，并带有单调递增的
`version`。请求不能自己携带或覆盖生命、护盾、状态、技能次数和回合结果，只能携带
`battle_id`、玩家身份及要执行的命令。服务器按以下顺序处理：

1. 根据 `battle_id` 读取当前快照和版本号。
2. 从快照恢复规则控制器并校验命令。
3. 仅当数据库版本仍等于读取版本时保存新快照，并原子递增版本号。
4. 版本冲突时，抢招请求根据最新快照重新校验；阶段推进请求返回
   `VERSION_CONFLICT`，不能自动推进最新阶段。

单进程内还应按 `battle_id`
串行执行请求，减少无意义的版本冲突。多进程和多实例部署必须使用 Postgres、Redis
等所有实例共享的仓库；进程内 Map
只可用于测试和本地单实例运行。这样两个玩家即使来自不同设备、请求落到不同服务实例，也会竞争同一条对局记录，而不会各自创建一份状态。

### 3.4 战斗阶段

#### 进入阶段

行动校验通过后，服务器将回合状态从 `WAITING_COMMAND` 改为
`SETTLING`，锁定本回合行动者和技能。此后该技能必须完整结算，不存在施法打断、半途取消或双方同时结算。

#### 执行动作

服务器使用服务端配置中的 `skill_id`、`effect_version` 和行动者当前状态计算行动：

1. 确定技能目标和技能效果参数。
2. 根据行动者的 Buff、生命、护盾和其他状态计算最终效果。
3. 依次应用伤害、护盾、治疗、增益、减益、DOT、破盾、驱散或一回合行动限制。
4. 将生命值、护盾和状态限制在服务器定义的边界内。
5. 记录技能使用次数和最近使用回合。

示例：行动者使用攻击技能时，服务器根据技能基础伤害、行动者增益和目标护盾计算实际扣除的护盾与生命；客户端只接收最终结果，不参与计算。

#### 结果通知

战斗阶段完成后，服务器向双方发送同一份权威事件，至少包含：

- 本回合成功行动的玩家和角色。
- 成功使用的标准技能名称和 `skill_id`。
- 行动造成的伤害、治疗、护盾和其他效果明细。
- 行动结算前后的双方生命、护盾和状态摘要。
- 当前回合是否产生死亡或终局。

建议事件类型为
`ACTION_ACCEPTED`、`BATTLE_RESULT`。服务器必须先持久化结果和事件，再向客户端广播，避免客户端看到无法恢复的临时结果。

### 3.5 回合结束阶段

#### 结束结算顺序

战斗阶段结果持久化后，服务器将回合状态改为
`ENDING`，按固定顺序处理回合结束效果：

1. 处理持续伤害（DOT）和周期性伤害。
2. 处理周期治疗、回合结束治疗或其他恢复效果。
3. 更新 Buff、Debuff 和行动限制状态的剩余回合数。
4. 移除持续时间已经归零的效果，并记录效果结束事件。
5. 再次检查双方生命值和死亡状态。

以上顺序必须由服务器固定实现并写入测试。后续如果某个新效果需要改变结算优先级，应增加明确的效果优先级配置，不能依赖代码执行顺序。

#### 结束阶段结果

- 如果回合结束效果导致一方生命值小于等于 0，立即结束对局，不创建下一回合。
- 如果双方仍存活，记录
  `ROUND_FINISHED`，发送完整回合结果，然后创建下一回合并回到 `WAITING_COMMAND`。
- 回合结束阶段不重新抢行动权；本回合已经确定的行动者不会改变。
- 回合结束效果不额外消耗技能使用次数，除非技能配置明确把效果定义为一次新的技能行动。
- 如果双方都因行动限制而无法行动，本回合不产生技能行动，直接进入回合结束阶段；不消耗任何技能次数。

### 3.6 对局流程总览

首版一局按照以下顺序执行：

```text
1. 匹配对手
   -> 2. 匹配成功，进入准备阶段
   -> 3. 双方准备完毕，开始对局
        -> 回合 1
        -> 回合 2
        -> 回合 3
        -> ...
   -> 4. 一方生命值归 0，对局结束
   -> 返回准备阶段
```

“返回准备阶段”表示客户端回到下一局可选择角色和查看技能的准备界面；上一局战斗记录进入只读归档，不复用上一局的生命、技能次数或
Buff 状态。

### 3.7 匹配对手

#### 玩家行为

1. 玩家进入匹配队列。
2. 匹配服务找到另一个符合条件的玩家。
3. 系统创建 `battle_id` 和对局房间，将双方加入同一战斗上下文。

#### 服务器状态与实现

- 匹配服务负责匹配，不负责技能和战斗结算。
- 战斗服务创建对局记录，状态为 `MATCH_CREATED`。
- 服务器校验双方身份、房间权限和客户端协议版本。
- 任一方取消匹配或匹配失败时，不创建可战斗回合。

#### 阶段结束

双方成功进入同一房间后，进入准备阶段。匹配阶段不消耗技能次数，也不创建
`ROUND_STARTED` 事件。

### 3.8 准备阶段

#### 玩家行为

1. 玩家选择一个角色。
2. 客户端展示该角色的 1 个基础技能、6 个角色技能、技能效果和使用规则。
3. 玩家可以熟悉角色技能和进入练习模式；练习模式不写入正式对局状态。
4. 玩家点击准备，等待另一方准备完成。

#### 服务器状态与实现

- 对局状态为 `PREPARING`，双方分别维护 `PLAYER_READY` 标记。
- 服务器根据 `character_id` 读取角色和技能配置，不能接受客户端上传的技能数值。
- 服务器在准备阶段校验技能名称唯一、无同音冲突、无自定义快捷词和无非法别名。
- 双方未准备完毕前，不创建第一回合，不接受战斗指令。

#### 阶段结束

双方准备完毕后，服务器初始化战斗快照：生命值、护盾、技能使用次数、最近使用回合和
Buff 全部按角色初始配置生成，然后进入对局开始阶段。

### 3.9 开始对局并执行回合

1. 服务器将对局状态改为 `RUNNING`。
2. 服务器创建第一个回合，设置 `round_no = 1` 和
   `round_status = WAITING_COMMAND`。
3. 服务器广播 `BATTLE_STARTED` 和 `ROUND_STARTED`。
4. 双方按 3.3-3.5 的三个回合阶段循环行动。
5. 每次回合结束后，只有双方仍存活时才创建下一回合。

### 3.10 对局结束并回到准备阶段

#### 结束条件

以下任一情况会结束正式对局：

- 战斗阶段直接造成一方生命值小于等于 0。
- 回合结束阶段的 DOT 或其他结束效果造成一方生命值小于等于 0。
- 双方同时因规则效果死亡时，按服务器预先定义的效果顺序记录结果；如无法区分先后，按平局处理。
- 房间发生不可恢复的服务器异常，进入异常结束状态，不伪造战斗胜负。

首版不设置单局和单回合玩法时长上限；房间回收、断线清理属于基础设施策略，不作为生命值或行动权判定。

#### 服务器处理

1. 标记死亡角色和胜负结果。
2. 设置对局状态为 `FINISHED`，拒绝后续战斗指令。
3. 持久化最终快照、最终技能使用记录和 `BATTLE_FINISHED` 事件。
4. 向双方发送胜者、败者、最终状态和对局结束原因。
5. 将战斗记录置为只读归档，清理房间运行态。

#### 回到准备阶段

客户端收到 `BATTLE_FINISHED`
后展示结算页；用户离开结算页后回到准备界面，可以查看角色、熟悉技能并开始下一次匹配。新的对局必须重新创建
`battle_id`，不能复用上一局的技能次数和状态。

## 4. 设计边界

### 4.1 MVP 包含

- 1V1 实时对战
- 角色选择
- 每个角色 1 个基础技能和 6 个角色技能，共 7 个技能
- 语音识别技能名称
- 技能使用次数、重复间隔、生命值和护盾
- 按服务器接收顺序抢行动权的回合制流程
- 技能伤害、治疗、护盾、自身增益
- 对手减益、DOT、驱散、破盾和一回合行动限制
- 回合结算和下一回合准备；首版不设置单回合倒计时

### 4.2 MVP 不包含

- 施法打断
- 延长或缩短对手念咒时间
- 改变技能目标或行动顺序的强制效果
- 复杂地图移动和位置判定
- 语音聊天作为战斗判定依据

一个回合最多产生一个行动者。行动限制属于已定义的特殊效果，但只影响后续回合行动资格，不改变本回合已经接受的行动。

### 5.2 胜负判定

1. 一方生命值小于等于 0，立即判定该方失败。
2. 每回合只结算先获得行动权的一方技能。
3. 首版不设置单局时间结束判定；双方持续存活时继续进行回合。
4. 如果产品后续增加单局时间上限，才启用生命值百分比和护盾值百分比的平局判定。
5. 仍然相同则判定平局，不使用随机数强行决定胜负。

### 5.3 单局模式

- 一次匹配只创建一局战斗，不进行三局两胜或局间重置。
- 角色死亡后立即结算胜负并结束战斗。
- 单局不设置固定时长；如果双方持续提交无效技能，战斗会持续等待。
- 为避免异常房间长期占用资源，服务端可以设置与玩法无关的房间保底回收机制，例如断线后的回收策略；该机制不作为玩家回合超时或行动判定。

## 6. 语音出招规则

### 6.1 技能名称

- 每个角色的 7 个技能名称必须唯一，其中 1 个标记为基础技能。
- 技能名称不再统一长度；技能强度与念诵长度绑定。
- 基础技能建议 3-4 个汉字，中等技能建议 5-7 个汉字，终极技能建议 8-12 个汉字。
- 强力技能必须使用更长、更完整的技能名称，给对手更多抢先行动的机会。
- 技能名称不得包含同音字、同音词或仅靠声调区分的变体，避免系统语音识别产生歧义。
- 同一角色的技能名称、别名和展示文本不得形成同音冲突；首版不配置技能别名。
- 技能名称不应包含常见闲聊词，避免误触发。
- 客户端展示标准念法和练习入口，但战斗中只接受标准词条。

当前客户端使用系统语音识别把语音转换成文字，再调用战斗接口；客户端不向服务器提供可靠的实际语音长度、音频结束时间或客户端语音时间戳。因此，服务器使用“第一个收到的正确技能请求”作为本回合行动权判定。技能名称长度是自然形成的出招风险，不再额外计算语音持续时间。

首版不支持自定义技能快捷词。玩家只能念角色配置中的标准技能名称，服务器只匹配标准词条。

### 6.2 识别阶段

每回合双方同时进入
`WAITING_COMMAND`。玩家念完技能后，客户端把系统识别到的文字和请求标识提交给服务器。服务器只接受当前角色配置的标准技能名称。单回合没有玩法时长限制，直到有效技能被接受并结算，或战斗因角色死亡结束。

单个请求有以下状态：

```text
IDLE
  -> TRANSCRIBED     客户端得到文字
  -> VALIDATING      服务器校验技能名称和当前状态
  -> ACCEPTED        获得本回合行动权
  -> SETTLING        服务器结算技能
  -> RESOLVED        本回合结束
```

以下情况进入失败状态，不视为被打断：

- `ASR_FAILED`：没有得到文字，或文字不是当前角色技能。
- `SKILL_EXHAUSTED`：普通技能已经在本局使用过，本次请求不占用行动权。
- `BASIC_CONSECUTIVE_REJECTED`：基础技能上一回合刚使用过，本次请求不占用行动权。
- `REUSE_LIMIT_REJECTED`：特殊技能达到本局使用次数或重复间隔限制，本次请求不占用行动权。
- `ROUND_ALREADY_WON`：另一名玩家已经获得本回合行动权。
- `ACTOR_DEAD`：角色已经死亡。

### 6.3 出招顺序

服务器按照请求到达战斗房间事件循环的顺序判定行动权，不接受客户端上传的结束时间。第一个满足以下条件的请求获胜：

1. 请求属于当前回合。
2. 技能名称与当前角色技能完全匹配。
3. 角色存活。
4. 技能仍有可用次数，或满足该技能的重复使用规则。
5. 当前回合还没有行动者。

获胜请求被原子地写入
`round_winner_id`，随后立即进入结算。另一方之后即使提交了正确技能，也返回
`ROUND_ALREADY_WON`，不能在本回合行动。

示例：

```text
服务器先收到玩家 A 的“炽焰斩击”
服务器后收到玩家 B 的“圣盾展开”

结算结果：
1. A 获得本回合行动权
2. A 造成伤害
3. B 本回合失去行动机会
4. 开始下一回合
```

技能一旦被服务器接受，就必定完成结算，不存在施法打断。若技能将对手击杀，对手本回合没有结算中的技能，不需要额外处理打断。

### 6.4 回合结束

技能结算完成后：

1. 增加技能本局使用次数，并记录最近使用回合。
2. 按本章回合结束阶段规则处理生命、护盾、Buff、Debuff、DOT 和行动限制状态。
3. 记录 `ROUND_FINISHED` 事件。
4. 如果双方仍存活，进入下一回合准备。

首版没有“回合超时”分支。以下请求不会结束等待状态，也不会消耗技能次数：识别失败、技能不可用、角色已死亡或请求不属于当前回合。只要双方仍存活，回合会继续等待首个正确且可用的技能请求。

由于当前客户端没有可靠的语音结束时间，MVP
不做“同时完成”判定，也不使用客户端时间戳。若未来接入服务端音频识别，再单独评估公平的时间窗口。

## 7. 技能规则

### 7.1 技能槽位和使用次数

每个角色固定配置 7 个技能槽位：

| 槽位     | 数量 | 默认使用规则            | 设计目的                                             |
| -------- | ---: | ----------------------- | ---------------------------------------------------- |
| 基础技能 |    1 | `BASIC_NON_CONSECUTIVE` | 提供稳定的低收益行动，使用次数不限但不能连续回合使用 |
| 角色技能 |    6 | 默认 `ONCE_PER_MATCH`   | 提供角色的核心差异和技能组合                         |

角色技能中的少量特殊技能可以配置为
`LIMITED_REPEAT`，但必须明确每局次数和最小回合间隔。除基础技能外，所有技能默认每局成功使用一次；技能是否重复使用由服务器配置决定，不由客户端选择。

### 7.2 技能效果分类

一个技能可以包含多个效果，服务器按技能配置的效果顺序结算。首版效果分为以下六类：

| 效果类别     | 标识              | 目标       | 规则                                                           |
| ------------ | ----------------- | ---------- | -------------------------------------------------------------- |
| 削减血量     | `DAMAGE`          | 对方       | 先扣除对方护盾，再扣除生命值；伤害受攻击增益和防御减益影响     |
| 回复自身血量 | `HEAL`            | 自身       | 恢复生命值，不得超过生命上限；可配置立即治疗或回合结束周期治疗 |
| 添加护盾     | `SHIELD`          | 自身       | 增加护盾，不得超过护盾上限；破盾效果可以移除全部或指定数值护盾 |
| 添加自身增益 | `SELF_BUFF`       | 自身       | 分为防御型和进攻型，可按持续回合或触发次数消耗                 |
| 添加对方减益 | `OPPONENT_DEBUFF` | 对方       | 分为进攻型和防御型，可包含 DOT、降低对方伤害等效果             |
| 特殊效果     | `SPECIAL`         | 自身或对方 | 破除护盾、附加一回合行动限制、解除对方增益、解除自身减益等     |

#### 增益和减益方向

- 防御型自身增益：持续回复生命、减少受到的伤害、提高护盾获得量等。
- 进攻型自身增益：提高伤害、提高特定技能伤害、提高 DOT 伤害等。
- 进攻型对方减益：附加 DOT、提高对方受到的伤害、降低对方治疗效果等。
- 防御型对方减益：降低对方造成的伤害、降低对方护盾或治疗效果等。

### 7.3 特殊效果和一回合行动限制

`SPECIAL` 可以配置以下效果：

- `BREAK_SHIELD`：解除对方全部护盾，或按配置削减指定护盾值。
- `REMOVE_OPPONENT_BUFF`：解除对方一个、多个或指定标签的增益。
- `CLEANSE_SELF_DEBUFF`：解除自身一个、多个或指定标签的减益。
- `ACTION_RESTRICTION`：令对方下一次行动阶段无法行动，状态名称可以是石化、麻痹或冻结。

行动限制只影响下一次回合开始阶段的行动资格，不会打断已经被服务器接受的技能，也不会撤销已经产生的战斗结果。技能在第
N 回合附加的 1 回合行动限制，默认作用于第 N+1 回合。被限制行动的玩家返回
`ACTION_DISABLED`，不消耗技能次数；如果双方都被限制行动，本回合直接进入回合结束阶段。

控制状态的默认规则：

1. 同一玩家同一时间只保留一个行动限制状态。
2. 重复施加时默认刷新持续时间，不叠加多个“无法行动”层数。
3. 新施加的状态从下一回合开始计算持续回合；行动限制在被限制的回合结束阶段扣减持续时间，持续时间归零后移除。
4. 驱散、净化等效果只能移除配置允许移除的标签，不能绕过服务器状态校验。

### 7.4 状态效果结算

所有持续效果统一存储为状态对象：

```text
StatusEffect
- effect_id
- effect_type       BUFF / DEBUFF / DOT / ACTION_RESTRICTION
- effect_tag        OFFENSE / DEFENSE / CONTROL / HEAL_OVER_TIME
- source_player_id
- source_skill_id
- value
- remaining_rounds
- remaining_triggers
- stack_count
- dispellable
```

技能在战斗阶段附加状态，回合结束阶段按固定顺序处理：DOT
和周期伤害、周期治疗、更新上一回合已经生效的 Buff/Debuff
和行动限制剩余时间、移除过期状态，最后检查死亡。当前战斗阶段刚附加的状态从下一回合开始计时，不能在同一回合结束时被立即扣除。状态处理必须由服务器完成并记录事件，客户端只展示结果。

同类状态默认不无限叠加：重复施加时按技能配置选择“刷新持续时间”“取更高数值”或“增加层数”。未特别配置时采用刷新持续时间且取更高数值，DOT
也遵守单技能来源的最大层数限制，避免复读技能造成无限叠加。

### 7.5 通用技能配置

技能使用效果数组表达组合技能，服务器根据 `skill_id` 和 `effect_version`
读取完整配置：

```json
{
  "skill_id": "flame_breaker",
  "slot_type": "CHARACTER",
  "name": "焚炎破阵诀",
  "cast_phrase": "焚炎破阵诀",
  "phrase_length_tier": "MEDIUM",
  "reuse_rule": "ONCE_PER_MATCH",
  "max_uses_per_match": 1,
  "min_round_gap": 0,
  "effects": [
    { "type": "DAMAGE", "target": "OPPONENT", "value": 120 },
    {
      "type": "OPPONENT_DEBUFF",
      "tag": "DOT",
      "value": 25,
      "duration_rounds": 2
    }
  ],
  "effect_version": 1
}
```

客户端只能提交标准技能名称对应的转写文字。伤害、治疗、护盾、持续时间、触发次数、驱散范围和行动限制都必须由服务器配置决定。

技能使用规则固定为三类：

- `ONCE_PER_MATCH`：每局只能成功使用一次。
- `BASIC_NON_CONSECUTIVE`：基础技能使用次数不限，但使用后下一回合不可再次使用；第
  N 回合使用后，第 N+2 回合可以再次使用。
- `LIMITED_REPEAT`：特殊技能可以使用多次，由 `max_uses_per_match` 和
  `min_round_gap` 共同限制。

### 7.6 技能可用性判定

```text
skillUsable(state, skill, currentRound):
    usage = state.skill_usage[skill.skill_id]
    lastRound = state.skill_last_used_round[skill.skill_id]

    if skill.reuse_rule == ONCE_PER_MATCH:
        return usage == 0
    if skill.reuse_rule == BASIC_NON_CONSECUTIVE:
        return lastRound == null or currentRound - lastRound >= 2
    if skill.reuse_rule == LIMITED_REPEAT:
        return usage < skill.max_uses_per_match \
            and (lastRound == null or currentRound - lastRound >= skill.min_round_gap)
```

### 7.7 推荐的数值区间

| 效果方向     | 建议念法长度 | 默认使用规则               | 效果区间                                |
| ------------ | -----------: | -------------------------- | --------------------------------------- |
| 快速小技能   |         4 字 | 每局 1 次或有限重复        | 60-90 伤害，或单一低数值效果            |
| 基础技能     |       3-4 字 | 不限次数，但不能连续两回合 | 50-80 伤害                              |
| 单次强力伤害 |       5-7 字 | 每局 1 次                  | 110-170 伤害                            |
| 治疗或护盾   |       5-7 字 | 每局 1 次                  | 90-180 治疗或 120-220 护盾              |
| 自身增益     |       5-8 字 | 每局 1 次或 2 次           | 持续 2-3 回合或 2-3 次触发              |
| 对方减益/DOT |       5-8 字 | 每局 1 次或有限重复        | 持续 2-3 回合，避免单次收益超过直接伤害 |
| 破盾/驱散    |       5-8 字 | 每局 1 次                  | 解除一个目标类别或 100%-200% 基础护盾   |
| 行动限制     |      8-12 字 | 每局 1 次                  | 对方下一回合无法行动                    |

技能强度和念法长度是同一套平衡的一部分。每个角色的 6 个角色技能建议包含 2
个快速小技能、3 个中型技能和 1
个长技能：快速小技能用于抢回合或补伤害，中型技能承担主要效果，长技能承担终极、强驱散或行动限制。行动限制、强力驱散和复合效果技能必须使用较长的标准名称，并通常配置为每局一次。

快速小技能仍然会消耗本局使用次数，不能被当作无成本的普通攻击。玩家需要在“短名称、较低收益、较高抢行动概率”和“长名称、高收益、较高被抢风险”之间选择；当本回合只需要稳定拿到行动权时，快速小技能应成为明确的策略选项。

### 7.8 技能长度平衡

`phrase_length_tier` 和 `reuse_rule`
用于策划校验和内容管理。服务器不测量真实语音长度，只校验最终转写文字是否完全匹配技能词条，并根据使用次数、状态和回合规则判断技能是否可用。

## 8. 首批角色示例

首批角色统一采用“1 个基础技能 + 6
个角色技能”的结构，基础技能全部是伤害型进攻技能：

| 角色     | 战斗定位       | 基础技能 | 主要策略                          |
| -------- | -------------- | -------- | --------------------------------- |
| 烈焰剑士 | 进攻爆发       | 破风斩   | 快速突刺、进攻增益、破甲、斩杀    |

| 安魂微光         | `HEAL`                       | 每局最多 2 次，间隔至少 2 回合     | 短（4 字） | 恢复 65 生命；不附加其他状态                               |
| 圣甲护身诀       | `SHIELD`、`SELF_BUFF`        | 每局 1 次                          | 中（5 字） | 获得 210 护盾，并获得 2 回合“受到伤害降低 20%”增益         |
| 回春守势诀       | `HEAL`、`SELF_BUFF`          | 每局 1 次                          | 中（5 字） | 立即恢复 100 生命，并在接下来 2 个回合结束时各恢复 45 生命 |
| 圣光净化万象咒   | `SPECIAL`                    | 每局 1 次                          | 中（7 字） | 解除自身和对方的全部可驱散减益/增益                        |
| 神圣壁垒永昼长明 | `ULTIMATE`、`SHIELD`、`HEAL` | 每局 1 次                          | 长（8 字） | 获得 280 护盾并恢复 120 生命；本回合不附加行动限制         |

技能循环：需要低风险快速行动时使用 `护阵回击` 或 `安魂微光`；使用
`圣甲护身诀`建立防守窗口，`回春守势诀`承担续航；`圣光净化万象咒`用于处理敌方
DOT、增伤或减伤状态。

定位：增益管理和复合收益。自身直接伤害不高，但通过多种进攻、防御增益提高后续技能价值。

| 技能             | 主要效果/标签                     | 使用规则                           | 念法长度   | 建议效果                                                |
| ---------------- | --------------------------------- | ---------------------------------- | ---------- | ------------------------------------------------------- |
| 蚀魂弹           | `DAMAGE`                          | 基础技能，不限次数但不能连续两回合 | 短（3 字） | 造成 60 伤害                                            |
| 咒火弹           | `DAMAGE`、`SELF_BUFF`             | 每局 1 次                          | 短（3 字） | 造成 75 伤害；下一次技能的首个效果提高 10%              |

| 血契回流式       | `HEAL`、`SELF_BUFF`               | 每局 1 次                          | 中（5 字） | 恢复 110 生命；获得 2 回合增益，治疗效果提高 25%        |

技能循环：需要快速准备时使用 `咒火弹` 或 `灵息聚能`，再用
`幽冥增幅契`和`虚空咒能聚合`叠加中期收益；`血契回流式`调整生命，最后以
`万咒归源幽冥禁章`完成复合收益。增益技能本身伤害低，不能连续使用同一增益形成无限叠加。

## 9. 后台技术实现

### 9.1 权威边界

客户端负责：

- 麦克风采集
- 语音活动检测
- 展示候选技能和识别进度
- 播放技能动画和音效
- 展示服务器下发的战斗结果

战斗服务器负责：

- 创建和推进回合
- 验证技能是否属于当前角色
- 验证技能使用次数和重复间隔
- 按请求到达顺序原子地抢占回合行动权
- 计算技能效果
- 更新生命、护盾、技能使用记录和全部状态效果
- 判定胜负
- 记录完整战斗日志

客户端不能直接提交以下字段：

- 伤害值
- 治疗值
- 护盾值
- 技能剩余使用次数
- 技能最近使用回合
- 技能是否命中
- 战斗胜负

### 9.3 行动处理伪代码

```text
acceptRoundCommand(command):
    round = loadRound(command.battle_id, command.round_no)
    state = loadPlayerState(command.player_id)
    skill = matchSkillByExactText(state.character_id, command.transcribed_text)

    if !round.isWaitingCommand():
        reject(command, ROUND_ALREADY_WON)
        return
    if !state.alive:
        reject(command, ACTOR_DEAD)
        return
    if state.action_state == ACTION_DISABLED:
        reject(command, ACTION_DISABLED)
        return
    if skill == null:
        reject(command, ASR_FAILED)
        return
    if !skillUsable(state, skill, command.round_no):
        reject(command, usageRejectReason(state, skill, command.round_no))
        return

    transaction:
        round = lockRound(command.battle_id, command.round_no)
        if !round.isWaitingCommand():
            reject(command, ROUND_ALREADY_WON)
            return
        round.round_winner_id = command.player_id
        round.round_status = SETTLING
        save(round, command)

    recordSkillUsage(command.player_id, skill, round.round_no)
    return ACCEPTED

advanceBattlePhase(battle_id):
    round = loadCurrentRound(battle_id)
    if round.round_status == SETTLING:
        settleRoundWinner(round)
        return
    if round.round_status == ENDING:
        settleRoundEnd(round)
        return
    reject(ROUND_NOT_WAITING)

settleRoundWinner(round):
    snapshot = loadBattleSnapshot(round.battle_id)
    skill = loadAcceptedSkill(round.skill_id)
    battleResult = calculateSkill(snapshot, round.round_winner_id, skill)
    applyResult(snapshot, battleResult)
    persistSnapshotAndEvents(snapshot, BATTLE_RESULT)

    if !battleStillRunning(snapshot):
        finishBattle(snapshot, round.battle_id)
        return

    round.round_status = ENDING

settleRoundEnd(round):
    snapshot = loadBattleSnapshot(round.battle_id)
    endResult = applyEndRoundEffects(snapshot, round.round_no)
    persistSnapshotAndEvents(snapshot, endResult)

    if battleStillRunning(snapshot):
        persistRound(snapshot, round, ROUND_FINISHED)
        createNextRound(round.battle_id)
    else:
        finishBattle(snapshot, round.battle_id)
```

`round_winner_id`
必须通过数据库行锁、乐观锁版本号或房间内单线程事件循环原子写入，保证两个几乎同时到达的请求只有一个获胜。普通
HTTP 请求的到达顺序不能直接作为数据库写入顺序，必须经过战斗房间的顺序化处理。

### 9.4 语音识别建议

- 战斗识别使用当前角色已配置的 7 个技能受限词表。
- 客户端通过系统语音识别得到文字，再调用回合指令接口。
- 客户端可以本地预识别以降低反馈延迟，但服务器仍需校验文字是否为当前角色技能。
- MVP 不依赖音频片段、语音持续时间或客户端结束时间，只使用服务器收到请求的顺序。
- 不设置请求防抖时间、不等待固定窗口，也不因前一请求未返回而延迟后续请求；每个到达服务器的请求立即进入校验流程。
- `command_id` 仅用于网络重试幂等和日志关联，不用于防抖或人为延迟行动判定。
- 语音识别由客户端系统完成；服务器不依赖客户端上传的识别置信度，最终以标准技能文本精确匹配为准。
- 需要提供念咒练习模式，展示标准发音和识别结果，但练习结果不直接写入战斗状态。

## 10. 关键异常规则

| 场景                                  | 处理方式                                                         |
| ------------------------------------- | ---------------------------------------------------------------- |
| 语音未识别或文字不匹配                | 不占用行动权，返回 `ASR_FAILED`                                  |
| 念到一半停止                          | 客户端不提交指令，继续等待本回合首个有效请求                     |
| 普通技能已经使用过                    | 不占用行动权，返回 `SKILL_EXHAUSTED`                             |
| 基础技能上一回合使用过                | 不占用行动权，返回 `BASIC_CONSECUTIVE_REJECTED`                  |
| 特殊技能达到次数或间隔限制            | 不占用行动权，返回 `REUSE_LIMIT_REJECTED`                        |
| 对手已经获得行动权                    | 本回合不再结算，返回 `ROUND_ALREADY_WON`                         |
| 行动者处于石化、麻痹或冻结状态        | 不占用行动权，返回 `ACTION_DISABLED`                             |
| 技能附加 DOT、Buff、Debuff 或行动限制 | 由服务器写入状态效果，按持续回合规则结算                         |
| 破盾、驱散或净化目标不存在对应状态    | 记录 0 效果结果，不视为请求失败，不返还技能次数                  |
| 回合内重复提交                        | 通过 `command_id` 幂等，不重复抢占行动权                         |
| 单回合长时间无人出招                  | 不触发玩法超时；继续等待有效请求，异常断线场景按房间回收策略处理 |
| 客户端断线                            | 保留战斗状态，等待 10 秒重连                                     |
| 重连后重复提交                        | 通过 `command_id` 幂等处理                                       |
| 服务器结算失败                        | 房间暂停并重试，不允许客户端自行补算                             |

## 11. 测试验收标准

1. 相同技能在相同状态下，服务器计算结果必须一致。
2. 客户端伪造伤害或技能使用记录不能改变战斗结果。
3. 第一个正确且可释放的请求必须获得本回合行动权。
4. 行动权写入后，后到达的正确技能必须返回 `ROUND_ALREADY_WON`。
5. 回合获胜技能只能结算一次，并且结算完成后才能进入下一回合。
6. 普通技能第二次请求必须被拒绝，基础技能连续两回合请求必须被拒绝。
7. 特殊重复技能必须遵守本局次数和最小回合间隔。
8. 技能长度越长，应该对应更高的使用收益或更高的抢行动风险。
9. 语音识别失败不能扣除技能使用次数。
10. 已用尽或不满足重复规则的技能请求不能占用本回合行动权。
11. 重复提交同一个 `command_id` 不能重复造成伤害或重复抢占行动权。
12. 单回合没有时长上限；无效请求不会推进回合或消耗技能。
13. 每个角色必须恰好配置 1 个基础技能和 6 个角色技能。
14. 治疗不能超过生命上限，护盾不能超过护盾上限，伤害必须先扣护盾再扣生命。
15. Buff、Debuff、DOT
    和周期治疗必须按配置的持续回合或触发次数结算，并在到期后移除。
16. 石化、麻痹和冻结只能阻止下一次行动阶段，不能打断已经接受的行动，也不能叠加多个行动限制层数。
17. 破盾、解除对方增益和解除自身减益只能影响配置允许驱散的状态。
18. 断线重连后，客户端状态必须以服务器快照为准。
19. 战斗日志能够还原每次文字识别、行动权抢占、结算和拒绝原因。
20. 在不同网络延迟下，结果以服务器收到有效请求的先后为准，服务器不增加防抖等待。
21. 技能名称存在同音字、同音词或同音别名时，内容审核和配置校验必须拒绝发布。
22. 客户端提交自定义快捷词时，服务器必须拒绝并按标准技能名称匹配。

## 12. 首版已确定约束

- 首版采用单局模式，不进行三局两胜。
- 语音识别由客户端系统完成，服务器只接收识别后的文字。
- 单回合不设置玩法时长限制。
- 每个角色固定为 1 个基础技能和 6 个角色技能。
- 技能支持伤害、治疗、护盾、自身增益、对方减益和特殊效果；特殊效果可包含破盾、驱散和一回合行动限制。
- 行动限制只阻止下一回合行动，不打断已经接受的行动。
- 技能名称不得包含同音字、同音词或同音别名。
- 服务器请求不设置防抖时间，收到请求后立即校验。
- 不支持自定义技能快捷词。
